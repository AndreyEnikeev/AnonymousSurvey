# Журнал расхождений с ЛР №2

## D-01. LLM-оркестратор, внешний провайдер, эндпоинт O-11 — не реализуются
- **В ЛР №2:** Контейнер C-06, C-12, эндпоинт O-11.
- **В реализации ЛР №3:** отсутствуют. Таблица `llm_classifications` оставлена.
- **Причина:** п. 4 ЛР №3 прямо исключает интеграцию с языковой моделью.

## D-02. Внешний сервис почтовых уведомлений → MailHog
- **В ЛР №2:** R-06 / C-13.
- **В реализации ЛР №3:** MailHog — локальная SMTP-заглушка.
- **Причина:** п. 4 ЛР №3 разрешает заменять коммерческие сервисы локальными заглушками.

## D-03. Транспорт Gateway → Auth: HTTP вместо gRPC+mTLS, TLS отложен
- **В ЛР №2:** таблица 4, связи L-05/L-06/L-07 — «gRPC с mTLS»; граница B-1 — TLS-терминация на Gateway.
- **В реализации ЛР №3:** YARP проксирует HTTP (`http://localhost:5135`). Контракты (пути, методы, коды ответов) сохранены. TLS не настроен.
- **Причина:** самоподписанный сертификат Auth в dev ломает YARP (`SslException`); mTLS требует инфраструктуры сертификатов, избыточной в dev. JWT валидируется дважды — в Gateway и в Auth (defense in depth), обход Gateway не даёт доступа.
- **Планируется:** заменить на gRPC+mTLS и настроить TLS на внешнем балансировщике при развёртывании в Docker (Этап 7).

## D-04. Упрощение проверки прав на объект для O-08 и O-09 (Периоды)
- **В ЛР №2:** п. 2.2.3 (O-09) и п. 2.2.4 (O-07): «Проверяется, что период относится к подразделению сотрудника».
- **В реализации ЛР №3:** проверка принадлежности к подразделению не реализована. Администратор (R-04) может видеть и изменять статус любого периода.
- **Причина:** в схеме БД (ЛР №2) у таблицы `users` нет поля `department` (подразделение есть только у `teachers`). Связать администратора с подразделением в текущей схеме невозможно без её изменения.
- **Компенсация:** проверка ролей (`[Authorize(Roles = "3")]`) работает. Ограничение доступа реализовано на уровне роли, а не конкретного объекта.

## D-05. Уточнение прав БД для surveys_service на таблицу users
- **В ЛР №2:** п. 3.5 подразумевает `GRANT SELECT ON users` для чтения данных пользователей.
- **В реализации ЛР №3:** выдан ограниченный доступ `GRANT SELECT (id, login) ON users`.
- **Причина:** сервису анкетирования нужен только логин преподавателя для отображения в заголовке анкеты (O-13). Email и хеши паролей сервису не нужны. Это усиление принципа наименьших привилегий.

## D-06. Дополнительное право `SELECT` на audit_events для surveys_service
- **В ЛР №2:** п. 3.5 указано только `GRANT INSERT ON audit_events` (сервис пишет логи).
- **В реализации ЛР №3:** выдано `GRANT INSERT, SELECT ON audit_events`.
- **Причина:** при выполнении `INSERT` EF Core использует конструкцию `RETURNING id`, чтобы получить сгенерированный первичный ключ. PostgreSQL требует право `SELECT` на таблицу для чтения возвращаемого значения.

## D-07. Использование MassTransit для работы с RabbitMQ
- **В ЛР №2:** брокер сообщений RabbitMQ, транспорт AMQP.
- **В реализации ЛР №3:** используется библиотека MassTransit поверх RabbitMQ.
- **Причина:** MassTransit — стандартная обёртка для .NET, которая упрощает публикацию и обработку сообщений, управляет топологией очередей и автоматически сериализует C#-объекты в JSON.

## D-08. Расширение прав БД для notifications_service
- **В ЛР №2:** п. 3.5 упоминает только `GRANT INSERT ON audit_events` и не упоминает права на таблицу `users` для сервиса уведомлений.
- **В реализации ЛР №3:** выданы права `GRANT SELECT (id, email, role_id) ON users` и `GRANT INSERT, SELECT (id) ON audit_events`.
- **Причина:** 
  1. Для формирования списка получателей сервису необходимо читать email-адреса и роли пользователей. 
  2. Для работы EF Core при `INSERT` в `audit_events` требуется право `SELECT (id)`, так как PostgreSQL использует конструкцию `RETURNING id` для возврата сгенерированного первичного ключа. Выдан доступ только к колонке `id`, что не нарушает принцип наименьших привилегий.

## D-09. Дополнение контракта события PeriodStatusChanged
- **В ЛР №2:** контракт события смены статуса периода не описан детально.
- **В реализации ЛР №3:** в контракт добавлено поле `PeriodName`, а также атрибуты `[EntityName]` и `[MessageUrn]`.
- **Причина:** 
  1. Поле `PeriodName` необходимо для формирования человекочитаемого текста письма (например, «Период "Осень 2026" закрыт»). 
  2. Атрибуты `[EntityName]` и `[MessageUrn]` жестко фиксируют имя очереди и URN сообщения, чтобы сервисы Surveys и Notifications могли общаться через RabbitMQ, несмотря на то, что они находятся в разных C#-пространствах имен (namespaces).

## D-10. Настройка Heartbeat для соединения с RabbitMQ
- **В ЛР №2:** не указаны параметры поддержания соединения с брокером.
- **В реализации ЛР №3:** в конфигурацию MassTransit добавлен параметр `h.Heartbeat(TimeSpan.FromSeconds(30))`.
- **Причина:** без регулярных пингов (heartbeat) брокер RabbitMQ разрывает простаивающее TCP-соединение, что приводит к генерации циклических логов ошибок в консоли сервисов и лишним переподключениям. Heartbeat обеспечивает стабильность соединения.

## D-11. Добавление поля full_name в таблицу users
- **В ЛР №2:** в таблице `users` отсутствовало поле для хранения ФИО пользователя.
- **В реализации ЛР №3:** в `schema.sql` добавлена колонка `full_name VARCHAR(255) NOT NULL`. Сущности `User` обновлены в сервисах Surveys и Analytics.
- **Причина:** для формирования человекочитаемых отчетов и заголовков анкет (вывода имени преподавателя вместо логина `teacher1`) необходимо хранить ФИО. В сервисах Auth и Notifications это поле не используется и не добавлялось, чтобы не раздувать код.

## D-12. Формат выгрузки отчетов (XLSX вместо CSV)
- **В ЛР №2:** в справочнике `export_formats` предусмотрены форматы `csv` и `xlsx`. 
- **В реализации ЛР №3:** сервис Аналитики (C-05) генерирует отчеты исключительно в формате `xlsx` (с использованием библиотеки ClosedXML).
- **Причина:** формат CSV не поддерживает несколько листов (вкладок) в одном файле. Для удобства руководства каждый шаблон анкеты выгружается на отдельный лист Excel, а на первом листе формируется общая сводка. Это также решает проблему с кодировкой кириллицы и разделителями дробных чисел.

---

## Что НЕ является расхождением

- **JWT валидируется и в Gateway, и в Auth.** Соответствует принципу defense in depth (п. 1.3 ЛР №2, границы B-2, B-3).
- **Rate Limiting — собственный middleware, а не пакет.** В ЛР №2 зафиксировано требование «ограничение частоты» (C-02), инструмент не указан. Свой middleware выбран для прозрачности и распределённого счётчика в Redis.
- **O-12 реализован в Auth, а не в Gateway.** Соответствует п. 1.2 ЛР №2: Gateway не имеет доступа к БД (граница B-4), данные аудита принадлежат Auth (C-03).
- **`GRANT SELECT ON audit_events TO auth_service`.** Соответствует п. 3.5 ЛР №2 (минимальные привилегии). Auth пишет аудит и читает его для O-12; `UPDATE` и `DELETE` не выданы.
- **`abortConnect=false` в строке подключения к Redis.** Стандартная настройка `StackExchange.Redis`, повышает устойчивость к порядку старта зависимостей в Docker Compose.
- **Таблица `ballots` не содержит `student_id`.** Соответствует п. 3.1 ЛР №2 (анонимность). Связь между тем, *кто* голосовал (`voter_checkins`) и *что* ответил (`ballots`), отсутствует намеренно.
