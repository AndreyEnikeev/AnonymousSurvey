# Журнал расхождений с ЛР №2

## D-01. LLM-оркестратор, внешний провайдер, эндпоинт O-11 — не реализуются
- **В ЛР №2:** Контейнер C-06, C-12, эндпоинт O-11.
- **В реализации ЛР №3:** отсутствуют. Таблица `llm_classifications` оставлена.
- **Причина:** п. 4 ЛР №3 прямо исключает интеграцию с языковой моделью.

## D-02. Внешний сервис почтовых уведомлений → MailHog
- **В ЛР №2:** R-06 / C-13.
- **В реализации ЛР №3:** MailHog — локальная SMTP-заглушка.
- **Причина:** п. 4 ЛР №3 разрешает заменять коммерческие сервисы локальными заглушками.

## D-03. Транспорт Gateway → Auth: HTTP вместо gRPC+mTLS, TLS отложен
- **В ЛР №2:** таблица 4, связи L-05/L-06/L-07 — «gRPC с mTLS»; граница B-1 — TLS-терминация на Gateway.
- **В реализации ЛР №3:** YARP проксирует HTTP (`http://localhost:5135`). Контракты (пути, методы, коды ответов) сохранены. TLS не настроен.
- **Причина:** самоподписанный сертификат Auth в dev ломает YARP (`SslException`); mTLS требует инфраструктуры сертификатов, избыточной в dev. JWT валидируется дважды — в Gateway и в Auth (defense in depth), обход Gateway не даёт доступа.
- **Планируется:** заменить на gRPC+mTLS и настроить TLS на внешнем балансировщике при развёртывании в Docker (Этап 7).

## D-04. Упрощение проверки прав на объект для O-08 и O-09 (Периоды)
- **В ЛР №2:** п. 2.2.3 (O-09) и п. 2.2.4 (O-07): «Проверяется, что период относится к подразделению сотрудника».
- **В реализации ЛР №3:** проверка принадлежности к подразделению не реализована. Администратор (R-04) может видеть и изменять статус любого периода.
- **Причина:** в схеме БД (ЛР №2) у таблицы `users` нет поля `department` (подразделение есть только у `teachers`). Связать администратора с подразделением в текущей схеме невозможно без её изменения.
- **Компенсация:** проверка ролей (`[Authorize(Roles = "3")]`) работает. Ограничение доступа реализовано на уровне роли, а не конкретного объекта.

## D-05. Уточнение прав БД для surveys_service на таблицу users
- **В ЛР №2:** п. 3.5 подразумевает `GRANT SELECT ON users` для чтения данных пользователей.
- **В реализации ЛР №3:** выдан ограниченный доступ `GRANT SELECT (id, login) ON users`.
- **Причина:** сервису анкетирования нужен только логин преподавателя для отображения в заголовке анкеты (O-13). Email и хеши паролей сервису не нужны. Это усиление принципа наименьших привилегий.

## D-06. Дополнительное право `SELECT` на audit_events для surveys_service
- **В ЛР №2:** п. 3.5 указано только `GRANT INSERT ON audit_events` (сервис пишет логи).
- **В реализации ЛР №3:** выдано `GRANT INSERT, SELECT ON audit_events`.
- **Причина:** при выполнении `INSERT` EF Core использует конструкцию `RETURNING id`, чтобы получить сгенерированный первичный ключ. PostgreSQL требует право `SELECT` на таблицу для чтения возвращаемого значения.

## D-07. Использование MassTransit для работы с RabbitMQ
- **В ЛР №2:** брокер сообщений RabbitMQ, транспорт AMQP.
- **В реализации ЛР №3:** используется библиотека MassTransit поверх RabbitMQ.
- **Причина:** MassTransit — стандартная обёртка для .NET, которая упрощает публикацию и обработку сообщений, управляет топологией очередей и автоматически сериализует C#-объекты в JSON.

## D-08. Расширение прав БД для notifications_service
- **В ЛР №2:** п. 3.5 упоминает только `GRANT INSERT ON audit_events` и не упоминает права на таблицу `users` для сервиса уведомлений.
- **В реализации ЛР №3:** выданы права `GRANT SELECT (id, email, role_id, full_name) ON users` и `GRANT INSERT, SELECT (id) ON audit_events`.
- **Причина:** 
  1. Для формирования списка получателей сервису необходимо читать email-адреса, роли и ФИО пользователей. 
  2. Для работы EF Core при `INSERT` в `audit_events` требуется право `SELECT (id)`, так как PostgreSQL использует конструкцию `RETURNING id` для возврата сгенерированного первичного ключа. Выдан доступ только к колонке `id`, что не нарушает принцип наименьших привилегий.

## D-09. Дополнение контракта события PeriodStatusChanged
- **В ЛР №2:** контракт события смены статуса периода не описан детально.
- **В реализации ЛР №3:** в контракт добавлено поле `PeriodName`, а также атрибуты `[EntityName]` и `[MessageUrn]`.
- **Причина:** 
  1. Поле `PeriodName` необходимо для формирования человекочитаемого текста письма (например, «Период "Осень 2026" закрыт»). 
  2. Атрибуты `[EntityName]` и `[MessageUrn]` жестко фиксируют имя очереди и URN сообщения, чтобы сервисы Surveys и Notifications могли общаться через RabbitMQ, несмотря на то, что они находятся в разных C#-пространствах имен (namespaces).

## D-10. Настройка Heartbeat для соединения с RabbitMQ
- **В ЛР №2:** не указаны параметры поддержания соединения с брокером.
- **В реализации ЛР №3:** в конфигурацию MassTransit добавлен параметр `h.Heartbeat(TimeSpan.FromSeconds(30))`.
- **Причина:** без регулярных пингов (heartbeat) брокер RabbitMQ разрывает простаивающее TCP-соединение, что приводит к генерации циклических логов ошибок в консоли сервисов и лишним переподключениям. Heartbeat обеспечивает стабильность соединения.

## D-11. Добавление поля full_name в таблицу users
- **В ЛР №2:** в таблице `users` отсутствовало поле для хранения ФИО пользователя.
- **В реализации ЛР №3:** в `schema.sql` добавлена колонка `full_name VARCHAR(255) NOT NULL`. Сущности `User` обновлены в сервисах Auth, Surveys, Analytics и Notifications.
- **Причина:** для формирования человекочитаемых отчетов и заголовков анкет (вывода имени преподавателя вместо логина `teacher1`), а также для отображения в шапке веб-клиента необходимо хранить ФИО.

## D-12. Формат выгрузки отчетов (XLSX вместо CSV)
- **В ЛР №2:** в справочнике `export_formats` предусмотрены форматы `csv` и `xlsx`. 
- **В реализации ЛР №3:** сервис Аналитики (C-05) генерирует отчеты исключительно в формате `xlsx` (с использованием библиотеки ClosedXML).
- **Причина:** формат CSV не поддерживает несколько листов (вкладок) в одном файле. Для удобства руководства каждый шаблон анкеты выгружается на отдельный лист Excel, а на первом листе формируется общая сводка. Это также решает проблему с кодировкой кириллицы и разделителями дробных чисел.

## D-13. Добавлен эндпоинт POST /api/auth/refresh
- **В ЛР №2:** в O-01 (`POST /api/auth/login`) указано, что выдаётся пара токенов (access + refresh), но отдельной операции для обновления пары по refresh-токену в перечне O-01…O-13 нет.
- **В реализации ЛР №3:** добавлен эндпоинт `POST /api/auth/refresh` — вне списка O-01…O-13.
- **Причина:** без этого метода refresh-токен, выдаваемый в O-01, невозможно применить. Клиент с истёкшим access-токеном был бы вынужден каждый раз проходить полный вход заново, что противоречит самому смыслу пары «access + refresh» и ухудшает UX.
- **Соответствие проекту:** требования безопасности ЛР №2 сохранены — access-токен короткоживущий, refresh-токен отзываемый (хранится в Redis), при выходе отзывается. Новое проектное решение (сам эндпоинт) зафиксировано здесь и не противоречит другим пунктам ЛР №2.

## D-14. Восстановление пароля (O-02) отправляется через RabbitMQ → Notifications → MailHog
- **В ЛР №2:** O-02 «запрос на восстановление доступа (отправка письма со ссылкой)» — письмо должно уходить через C-07 (Notifications) и R-06 (внешний сервис почтовых уведомлений).
- **В реализации ЛР №3 (до исправления):** в Auth (C-03) токен выводился в `Console.WriteLine` — это была временная заглушка, не связанная с R-06.
- **В реализации ЛР №3 (после исправления):** Auth публикует событие `PasswordResetRequested` в RabbitMQ, сервис Notifications получает его и отправляет письмо через MailKit в MailHog. Контракт `PasswordResetRequested` зафиксирован атрибутами `[EntityName]` и `[MessageUrn]` (по аналогии с `PeriodStatusChanged`, см. D-09), чтобы сообщение доходило между разными namespace.
- **Причина:** соответствие п. 4 ЛР №3 (замена коммерческого сервиса локальной заглушкой MailHog с сохранением контракта) и полное выполнение сценария O-02 из ЛР №2.

## D-15. В JWT access-токен добавлен claim full_name
- **В ЛР №2:** состав payload JWT описан в п. 2.4. Достаточно sub, login, role для авторизации и аудита.
- **В реализации ЛР №3:** добавлен дополнительный claim `full_name` (значение — `users.full_name` из D-11).
- **Причина:** веб-клиент (C-01) должен отображать в шапке имя пользователя (ФИО), а не логин. Отдельного эндпоинта «профиль текущего пользователя» в контракте ЛР2 нет.
- **Безопасность:** ФИО не является секретом, оно и так отображается в отчётах. JWT подписан, подделать claim нельзя. Gateway и Auth валидируют подпись, лишний claim на проверки не влияет.

## D-16. Проверка существования сессии в Redis на каждом запросе
- **В ЛР №2:** механизм проверки жизнеспособности сессии отдельно не описан. Cookie-auth + TTL access-токена считались достаточными.
- **В реализации ЛР №3:** между `UseAuthentication` и `UseAuthorization` в WebClient добавлен middleware, который для каждого аутентифицированного запроса проверяет существование ключа `web:session:{sessionId}` в Redis. Если ключа нет — сессия разлогинивается.
- **Причина:** cookie аутентификации имеет TTL 8 часов, а сессия в Redis может быть удалена раньше (например, при перезапуске контейнера). Middleware закрывает этот сценарий, перенаправляя пользователя на логин с явным сообщением, а не оставляя его с «мёртвым» API-токеном.

## D-17. Добавлено поле PeriodName в контракты O-04 и O-06
- **В ЛР №2:** контракты O-04 (список активных анкет) и O-06 (история) содержали только `periodId` (UUID).
- **В реализации ЛР №3:** в DTO добавлено строковое поле `periodName`.
- **Причина:** для отображения в веб-клиенте нужен человекочитаемый текст периода (например, «Осень 2026»). Отдавать клиенту только UUID и заставлять его делать дополнительный запрос — избыточно.

## D-18. В контракт O-07 (Агрегированный отчёт) добавлены названия сущностей
- **В ЛР №2:** DTO отчёта содержал только идентификаторы (disciplineId, teacherId, periodId).
- **В реализации ЛР №3:** добавлены поля `DisciplineName`, `TeacherName`, `PeriodName`.
- **Причина:** клиенту (C-01) для отображения таблицы нужны человекочитаемые названия. Возвращать GUID и заставлять клиент делать 3 дополнительных запроса к разным сервисам — избыточно и неэффективно.

## D-19. Добавлен CRUD для шаблонов анкет
- **В ЛР №2:** операции создания/редактирования шаблонов анкет (Survey Templates) и вопросов отсутствовали. Предполагалось, что они загружаются из seed-данных.
- **В реализации ЛР №3:** добавлены эндпоинты `GET /api/admin/surveys`, `GET /api/admin/surveys/{id}`, `POST /api/admin/surveys`, `PUT /api/admin/surveys/{id}`, `PATCH /api/admin/surveys/{id}/status`.
- **Причина:** для полноценной демонстрации работы системы на защите необходима возможность создавать и редактировать анкеты без прямого вмешательства в базу данных.
- **Безопасность:** редактирование заблокировано на сервере, если анкета находится в статусе `active`/`closed` (только `draft`). Дополнительно запрещено менять вопросы, если на анкету уже есть хотя бы один ответ (защита от искажения статистики).

## D-20. Добавлено создание периодов анкетирования
- **В ЛР №2:** операции создания периодов не было (только O-08 просмотр и O-09 смена статуса). Периоды загружались из seed.
- **В реализации ЛР №3:** добавлен эндпоинт `POST /api/admin/periods` и форма создания в веб-клиенте.
- **Причина:** для логичной работы администратора (создать период -> создать в нем анкеты -> опубликовать) необходимо уметь создавать сами периоды через UI. Новый период всегда создается в статусе `draft`.

## D-21. Добавлена таблица one_time_tokens
- **В ЛР №2:** в DDL-скрипте таблицы не было (упоминалась только в тексте п.3.3 «Связанные механизмы»).
- **В реализации ЛР №3:** добавлена таблица `one_time_tokens` (`user_id`, `purpose`, `token_hash`, `expires_at`, `used_at`, `created_at`). Хранится **хеш** токена, не сам токен.
- **Причина:** для полного сценария O-02 (восстановление доступа) нужен одноразовый токен со сроком действия и меткой использования. Хранение хеша защищает от компрометации при утечке дампа.

## D-22. В таблице ballots хранится только дата отправки, без точного времени
- **В ЛР №2:** `submitted_date DATE` — дата, без времени. Но в тексте п.3.1 обоснование отсутствовало.
- **В реализации ЛР №3:** `submitted_date date NOT NULL` — только дата, без `timestamptz`. Зафиксировано как осознанное решение.
- **Причина:** точное время отправки в сочетании с журналом `voter_checkins` (который знает `student_id` и время голосования) позволяет сопоставить timestamp и деанонимизировать студента. Атакующий с доступом к БД (например, техспец R-05) мог бы отсортировать `voter_checkins` и `ballots` по времени и восстановить связь «кто → что ответил», обойдя архитектурную анонимность (разделение таблиц без FK). Хранение только даты снижает этот риск: внутри одного дня сопоставление неоднозначно, а для отчётов по периодам (месяц/семестр) гранулярности «день» достаточно.
- **Ограничение:** атака «сопоставление по времени» ослаблена, но не исключена полностью — если в анкете проголосовал ровно один студент в конкретный день, связь восстанавливается. Это принято как остаточный риск; полное устранение потребовало бы задержки записи `ballots` (например, батчинг раз в сутки), что усложнило бы систему без выигрыша для учебного проекта.

## D-24. Уточнение D-06: surveys_service читает только колонку id из audit_events

## Что НЕ является расхождением

- **JWT валидируется и в Gateway, и в Auth.** Соответствует принципу defense in depth (п. 1.3 ЛР №2, границы B-2, B-3).
- **Rate Limiting — собственный middleware, а не пакет.** В ЛР №2 зафиксировано требование «ограничение частоты» (C-02), инструмент не указан. Свой middleware выбран для прозрачности и распределённого счётчика в Redis.
- **O-12 реализован в Auth, а не в Gateway.** Соответствует п. 1.2 ЛР №2: Gateway не имеет доступа к БД (граница B-4), данные аудита принадлежат Auth (C-03).
- **`GRANT SELECT ON audit_events TO auth_service`.** Соответствует п. 3.5 ЛР №2 (минимальные привилегии). Auth пишет аудит и читает его для O-12; `UPDATE` и `DELETE` не выданы.
- **`abortConnect=false` в строке подключения к Redis.** Стандартная настройка `StackExchange.Redis`, повышает устойчивость к порядку старта зависимостей в Docker Compose.
- **Таблица `ballots` не содержит `student_id`.** Соответствует п. 3.1 ЛР №2 (анонимность). Связь между тем, *кто* голосовал (`voter_checkins`) и *что* ответил (`ballots`), отсутствует намеренно.
- **Схема БД не генерируется через ORM.** Схема создается скриптом `schema.sql` через `docker-entrypoint-initdb.d`, что соответствует п. 2.1 ЛР №3. ORM (EF Core) используется только для маппинга существующих таблиц.
